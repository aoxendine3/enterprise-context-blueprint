### Executive Summary
This memorandum establishes the un-spared engineering requirements for autonomous agent governance, cryptographic attestation, formal tool-invocation safety, and tamper-evident logging. This document strictly enforces the fail-closed invariants required by NIST SP 800-53 Rev. 5, NIST SP 800-218 (SSDF), NIST AI RMF 1.0, and RFC 6962.

---

### 1. NIST AI RMF 1.0 and NIST SP 800-53 Rev. 5 Controls for Autonomous Agents
Traditional AI RMF 1.0 applications focused on static predictive models; autonomous LLM agents operating at machine speed require extreme interpretations of these frameworks.
* **GOVERN & MAP:** AI RMF requires mapping the exact boundary of autonomous capability. For agents, this maps to defining strict capability perimeters and identity profiles. Every agent must possess a unique, machine-verifiable identity (SPIFFE/SPIRE).
* **MEASURE & MANAGE:** Static policy governance is insufficient for unbounded LLM outputs. The MANAGE function mandates continuous, real-time monitoring of agent deviations and anomalous tool invocations (Deception-based detection, runtime behavioral bounds).
* **SP 800-53 Rev. 5 Mapping:**
    * **AU-2 / AU-10 (Event Logging & Non-repudiation):** Agent workflows must enforce non-repudiation of every LLM token generation that leads to a system action.
    * **AC-3 (Access Enforcement):** Dynamic, attribute-based access control (ABAC) must gate every agent tool invocation.
    * **SI-4 (System Monitoring):** Multi-stage validation of payload inputs generated by agents before OS-level execution.

### 2. Formal Semantic Verification vs. Static Python Heuristics
* **The Failure of Static String Matching:** Relying on Python `regex` or simple substring checks (e.g., `if "rm -rf" in command: block()`) fails NIST/DARPA verification because it is structurally blind to obfuscation, aliasing, and semantic equivalence. An adversarial LLM can bypass strings via base64 encoding, environment variable concatenation, or script-wrapping. 
* **SMT Solvers (Z3 / CVC5) & AST Formal Methods:** DARPA-hardened systems require Abstract Syntax Tree (AST) parsing and formal semantic verification. Before an agent executes a payload, the generated code must be lowered into a formal representation. SMT solvers (like Z3 or CVC5) mathematically prove that the proposed execution path does not violate predefined invariant constraints (e.g., proving a filesystem write will never traverse outside target perimeters). If the SMT solver cannot mathematically prove safety (`UNSAT`), the system fails closed.

### 3. RFC 6962: Merkle Tree Transparency vs. Local SQLite Logs
* **The SQLite Vulnerability:** Standard local SQLite logging is strictly mutable and susceptible to context pollution and trace erasure. A compromised agent could execute an unauthorized action and execute `DELETE FROM logs WHERE...` to erase its tracks.
* **RFC 6962 Merkle Tree Transparency:** Autonomous systems must adopt the Certificate Transparency (RFC 6962) architecture. Every agent thought, tool call, and state transition is hashed and appended as a leaf node in a Merkle tree.
    * **Asymmetric Signatures (Ed25519/ECDSA):** Each leaf is signed cryptographically, ensuring non-repudiation of the agent's identity.
    * **Inclusion & Consistency Proofs:** Auditors (or Trinity Gate evaluator agents) can request logarithmic-time cryptographic proofs that an action exists in the log (inclusion) and that the history has never been retroactively altered (consistency). This enforces a 100% tamper-evident, append-only lineage.

### 4. Hardware Root-of-Trust vs. Static HMAC Keys
* **Static HMAC Failure:** Local static HMAC keys stored in `.env` files or filesystem configurations are fundamentally vulnerable to memory-scraping, unauthorized file reads by the agent itself, or side-channel leakage.
* **Hardware Root-of-Trust (TPM 2.0 / Apple Secure Enclave):** True governance requires cryptographic operations to occur in isolated, tamper-proof hardware boundaries. 
    * Using TPM 2.0 or the Apple Secure Enclave, private keys are generated inside the silicon and can never be exported to the OS. 
    * When an agent must sign a Merkle leaf or authenticate a Trinity Gate payload, the hash is sent to the hardware enclave. The enclave signs it and returns the signature. 
    * This ensures that even a fully compromised root-level OS and rogue LLM agent cannot forge the cryptographic lineage or steal the signing keys.
